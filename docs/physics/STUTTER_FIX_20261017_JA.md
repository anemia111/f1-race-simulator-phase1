# Cinematic走行のカクつき修正・検証記録

確認日：2026-10-17。ローカル実装。コミット・push・公開サイト更新は実施していない。
ユーザー提供録画 `20261016-2336-42.3417949.mp4`（4.233秒、1120×782）の鈴鹿・TV・Medium表示を参照した。

## 修正内容

1. **受信時刻に基づく描画バッファ**：以前は100 ms分の物理更新を100 msで補間し、受信が200 ms間隔なら残り100 ms停止した。
   受信済みの確定フレームを約200 ms保持し、受信時刻上の同じ再生時刻を全車・カメラで共有する。
   未受信の未来位置は作らない。レース順位・タイム・AI判断を補間側で変更しない。
   停止操作、リセット、ピット・状態遷移、大きな不連続は補間から切り離す。
   古い路面グリッドやイベントログを保持せず、履歴数も24件に制限した。
2. **Workerの協調実行**：物理刻みは50 msを維持し、1倍は8 ms・高倍率は16 msの処理予算でタスクを区切る。
   1ステップ自体が予算を超える場合は、そのステップ終了後に譲る。高負荷時の追いつきキューは上限を設ける。
   スナップショット送信は1倍100 ms、5倍150 ms、20倍250 ms、60倍500 msを維持。
   高倍率で大きな路面スナップショットを過剰送信して描画負荷を増やさない。
3. **シャドウ追尾の整合**：光源・影もマシンと同じ描画バッファの位置を追う。最新の未補間位置へ影だけが飛ぶ経路を除去。
4. **距離と終端速度の分離**：通常走行の位置更新へ力積分の距離を接続した。
   平均走行速度を次の物理刻みの初速へ戻さず、終端速度を保持する。
   交通・旗・事故の制約で距離を切り詰める場合は、解決済みの走行ペースを外部の速度上限として扱う。
   移動量が小さいからといって、車列の後続車を負の速度推定から0 km/hへ落とさない。
   この外部制約をタイヤ制動や回生エネルギーとして架空に計上する処理は加えていない。

## 実GPUでの修正前後比較

比較元は前回納品した `f1-physics-ers-20261017-source.zip`。
読み取り専用の描画位置プローブのみ追加し、同じプローブを変更後にも使用した。
Intel Iris Xe / D3D11、1280×900、鈴鹿、22台、Medium、1倍速、同一seed、NAK選択。
各カメラを約8秒計測し、両方でブラウザ録画を有効にした。
描画フレームごとの位置を計測し、車速50 km/h以上・running状態で位置差が1e-10周未満を停止フレームと定義する。
カメラの意図的な切替を、マシン停止の判定と混同していない。

| chase | 15 / 480 | 0 / 479 | 25.2 ms | 37.4 ms |

変更後は3カメラとも、逆戻り0、未受信位置への先読み0。Pauseで位置保持、Resumeで前進を確認した。
この8秒区間の停止フレーム0を、全環境・全コース・長時間の無停止保証にはしない。
TVでは上表の単発の長い描画間隔が残る。ロード・GPU負荷・カメラ切替を含む長フレームの完全解消は未確認。
動画はブラウザ録画のフレームレートであり、描画プローブやGPUの実フレームレートとは別。
切り出し時に中間フレームの生成や動きの補正は行っていない。

## 残課題と対象範囲

この修正の主対象は、提供録画にあるCinematicのSIM・1倍速の周期的な停止。
車載／TVの全画角・全GPU・全品質で60fpsを保証する変更ではない。
交通・ピット・旗での外部位置制約の力学統合、MGU-K需要返却、Boost、複数コーナー軌跡最適化は別の残課題。
描画バッファは確定位置だけを利用するため、データが長時間届かなければ最終確定位置で待つ。
実時間の物理進行速度が要求倍率へ届くことも、今回の滑らかさの検証とは区別する。
